Gin 项目不需要只为了版本号而升级。存量服务更关注稳定性和依赖兼容，新项目则应结合 Go 工具链、部署环境和中间件支持情况选择版本。

## 版本选择

| 版本 | 典型场景 | 维护重点 |
| --- | --- | --- |
| Gin 1.9 | 运行稳定的存量服务 | 锁定依赖、补齐测试、逐步升级 |
| Gin 1.10 | 保守维护的常规 API 项目 | 参数绑定、中间件顺序、错误处理 |
| Gin 1.11 | 需要较新协议或表单能力的项目 | Go 版本、HTTP/3 链路、第三方中间件 |
| Gin 1.12 | 新项目或较新 Go 环境 | 工具链一致性、依赖兼容、部署验证 |

已经稳定运行的项目不必跨多个版本升级。准备长期迭代的新项目，则应优先选择团队能够持续维护的稳定版本。

## 查看和固定版本

查看当前版本：

```bash
go list -m github.com/gin-gonic/gin
```

指定版本后整理依赖：

```bash
go get github.com/gin-gonic/gin@v1.12.0
go mod tidy
go test ./...
```

`go.mod` 和 `go.sum` 应提交到版本库。本地、CI 与服务器使用的 Go 版本也要保持一致。

## 通用检查清单

| 检查项 | 说明 |
| --- | --- |
| 路由 | 分组、路径参数和通配符路由是否符合预期 |
| 中间件 | 鉴权失败后是否正确 `Abort()`，执行顺序是否稳定 |
| 参数绑定 | JSON、Query、Form、URI 和文件上传是否覆盖测试 |
| 错误处理 | panic recovery 和统一错误格式是否有效 |
| 代理配置 | 真实 IP、可信代理和转发请求头是否正确 |
| 日志 | 请求日志与业务错误日志是否能够关联 |

## Gin 1.9 存量项目

Gin 1.9 常见于运行时间较长的 API 服务。维护时先固定现有 Go 与依赖版本，再回归登录鉴权、参数校验、文件上传和中间件顺序。

```bash
go get github.com/gin-gonic/gin@v1.9.1
go mod tidy
```

如果业务稳定且改动很少，可以继续维护；计划持续迭代时，应建立测试基线后逐个版本升级。

## Gin 1.10 稳定维护

Gin 1.10 项目重点检查参数绑定、中间件、panic recovery 和日志。不要在升级 Gin 的同时大范围重构业务，否则出现问题时很难区分原因。

```bash
go get github.com/gin-gonic/gin@v1.10.1
go test ./...
```

## Gin 1.11 协议与兼容性

使用较新协议和表单能力前，需要确认反向代理、负载均衡、容器网络和客户端是否共同支持。HTTP/3 等能力只有在完整链路生效时才有意义。

```bash
go get github.com/gin-gonic/gin@v1.11.0
go mod tidy
go test ./...
```

升级后重点回归请求体绑定、文件上传、自定义中间件和错误响应格式。

## Gin 1.12 新项目

新项目可以使用较新版本，但应先确认 Go 工具链与部署环境满足要求。

```go
module example.com/api

go 1.25

require github.com/gin-gonic/gin v1.12.0
```

推荐按职责组织代码：

```text
cmd/
api/
internal/
handler/
service/
repository/
middleware/
```

简单项目可以减少分层，但不要把路由、业务逻辑和数据访问全部放进 `main.go` 或 handler。

## 升级步骤

1. 固定当前依赖并运行完整测试。
2. 记录核心接口的响应、性能和错误率基线。
3. 升级到相邻版本并阅读发布说明。
4. 回归路由、绑定、中间件、上传和错误分支。
5. 在测试环境观察日志与性能，再逐步发布。

具体路由、中间件和统一响应写法可继续阅读：[Gin 使用指南](/blog/wiki/backend/go-gin-guide/)。
