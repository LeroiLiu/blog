# Sidecar模式初识

<div class="migrated-article" v-pre>
<p>Sidecar设计模式正在收到越来越多的关注和采用。作为Service Mesh的重要要素&#xff0c;Sidecar模式对于构建高度高度可伸缩、有弹性、安全且可便于监控的微服务架构系统至关重要。而Service Mesh也已经被证明&#xff0c;正在改变企业IT的“游戏规则”&#xff0c;它降低了与微服务架构相关的复杂性&#xff0c;并提供了负载平衡、服务发现、流量管理、电路中断、遥测、故障注入等功能特性。</p>
<h3>什么是Sidecar模式&#xff1f;</h3>
<p>Sidecar模式是一种将应用功能从应用本身剥离出来作为单独进程的方式。该模式允许我们向应用无侵入添加多种功能&#xff0c;避免了为满足第三方组件需求而向应用添加额外的配置代码。</p>
<p>就像边车加装在摩托车上一样&#xff0c;在软件架构中&#xff0c;sidecar附加到主应用&#xff0c;或者叫父应用上&#xff0c;以扩展/增强功能特性&#xff0c;同时Sidecar与主应用是松耦合的。</p>
<p>举个例子&#xff0c;假设现在有6个相互通信的微服务&#xff0c;每个微服务都需要具有可观察性、监控、日志记录、配置、断路器等功能&#xff0c;而所有这些功能都是在微服务中使用一些第三方库实现的。</p>
<p>这样一组服务的实际情况可能会非常复杂&#xff0c;增加了应用的整体复杂性&#xff0c;尤其是当每个微服务用不同的语言编写、使用不同的基于.net、Java、Python等语言的第三方库……</p>
<h3>Sidecar模式的好处</h3>
<ul>
<li>通过将公用基础设施相关功能抽象到不同的层来降低微服务的代码复杂性</li>
<li>由于我们不需要在每个微服务中编写配置代码&#xff0c;因此减少了微服务架构中的代码重复</li>
<li>P应用和底层平台之间实现了松耦合</li>
</ul>
<h3>Sidecar模式如何工作</h3>
<p>Service Mesh层可以位于应用程序侧的Sidecar容器中&#xff0c;同一sidecar的多个副本可以附在每个应用旁。</p>
<p>来自单个服务的所有传入和传出网络流量均通过Sidecar代理&#xff0c;完成微服务之间的流量管理、遥测数据收集以及策略的执行等等。从某种意义上来说&#xff0c;服务对于网络是无感知的&#xff0c;只知道所附加的sidecar代理。这就是Sidecar模式工作的本质&#xff0c;它将网络依赖抽象成了Sidecar。</p>
<p><img alt="" src="/images/blog/87866522/local-001.png" /></p>
<p>在Service Mesh中&#xff0c;我们需要了解Data Plane和Control Plane两个概念——</p>
<ul>
<li>Data Plane的作用是处理网格内服务间的通信&#xff0c;并完成服务发现、负载均衡、流量管理、健康检查等功能&#xff1b;数据平面的作用是处理网格内服务之间的通信&#xff0c;并负责实现服务发现、负载平衡、流量管理、健康检查等功能&#xff1b;</li>
<li>Control Plane的作用是管理和配置Sidecar来执行策略并收集遥测&#xff08;telemetry&#xff09;</li>
</ul>
<h3>例子</h3>
<p>一些例子如下&#xff1a;<br /><br />
Web-server容器可以与一个sidecar容易共同部署&#xff0c;该sidecar容器从文件系统中读取由Web-server容器生成的web-server日志&#xff0c;并将日志/stream发送到原称服务器&#xff08;remote server&#xff09;。Sidecar容器通过处理web-server日志来作为web-server容器的补充。当然&#xff0c;可能会有人说&#xff0c;为什么web-server不自己处理自己的日志&#xff1f;答案在于以下几点&#xff1a;</p>
<ul>
<li>隔离&#xff08;separation of concerns&#xff09;&#xff1a;让每个容器都能够关注核心问题。比如web-server提供网页服务&#xff0c;而sidecar则处理web-server的日志&#xff0c;这有助于在解决问题时不与其他问题的处理发生冲突&#xff1b;</li>
<li>单一责任原则&#xff08;single responsibility principle&#xff09;&#xff1a;容器发生变化需要一个明确的理由。换句更容易理解的话来说&#xff0c;每个容器都应该是能够处理好“一件”事情的&#xff0c;而根据这一原则&#xff0c;我们应该让不同的容器分别展开工作&#xff0c;应该让它们处理的问题足够独立&#xff1b;</li>
<li>内聚性/可重用性&#xff08;<code>Cohesiveness/Reusability</code>&#xff09;&#xff1a;使用sidecar容器处理日志&#xff0c;这个容器按道理应该可以应用的其他地方重用&#xff1b;</li>
</ul>
