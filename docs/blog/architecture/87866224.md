<h2>什么是Service Mesh&#xff1f;</h2>
<p>根据Linkerd CEO William Morgan定义&#xff0c;Service Mesh是用于处理服务间通信的基础设施层&#xff0c;用于在云原生应用复杂的服务拓扑中实现可靠的请求传递。在实践中&#xff0c;Service Mesh通常是一组与应用一起部署&#xff0c;但对应用透明的轻量级网络代理。</p>
<p><img alt="" height="664" src="/images/blog/87866224/local-001.png" width="886" /></p>
<p>Service Mesh与传统基础设施层不同之处在于&#xff0c;它形成了一个分布式的互连代理网络&#xff0c;以sidecar形式部署在服务两侧&#xff0c;服务对于代理无感知&#xff0c;且服务间所有通信都由代理进行路由。</p>
<p><img alt="" height="665" src="/images/blog/87866224/local-002.png" width="887" /></p>
<h2>为什么需要Service Mesh&#xff1f;</h2>
<p>“Smart endpoint and dumb pipes”是微服务架构在集成服务时采用的一个核心理念&#xff0c;这一理念改变了过去臃肿集中的ESB&#xff08;企业服务总线&#xff09;&#xff0c;无疑是正确方向上的一大进步&#xff0c;但同时也给我们出了一些难题——多智能才不会过于智能&#xff0c;而服务轻重大小的程度如何拿捏&#xff1f;我们应该如何处理微服务系统中服务间交互的复杂性&#xff1f;放在服务内部还是外部&#xff1f;如果是内部&#xff0c;如何处理业务逻辑关系&#xff0c;或者应该与基础设施更为相关&#xff1f;如果是外部&#xff0c;如何避免重蹈ESB的覆辙&#xff1f;</p>
<p>皮的不谈&#xff0c;先来看看处理服务间通信时需要关注的点&#xff1a;</p>
<ul>
<li>服务发现</li>
<li>负载均衡</li>
<li>路由</li>
<li>流量控制</li>
<li>通信可靠性</li>
<li>弹性</li>
<li>安全</li>
<li>监控/日志</li>
</ul>
<p>似乎都是老生常谈&#xff0c;存在于任何需要处理网络的分布式系统之中&#xff0c;区别在于&#xff0c;当所涉及微服务数量呈指数级增加&#xff0c;这些问题也会被相应放大。</p>
<p>一个已经被广泛应用的解决方案是利用api网关来处理服务外部和服务之间的请求&#xff0c;提供例如服务发现、路由、监控、流量控制等。</p>
<p>然而&#xff0c;api网关有一个比较致命的缺陷&#xff0c;它容易出现单点故障并且实践不当很有可能会变得异常臃肿。另一方面&#xff0c;api网关核心是面向用户&#xff0c;也就是说它可以解决从用户到微服务的流量问题&#xff0c;但不能解决所有问题&#xff0c;而我们需要的是一个完整的方案&#xff0c;或者至少是一些能够与api网关互补的方案和工具。</p>
<p>另一种选择是在网络堆栈的较低层级&#xff08;4/3&#xff09;进行可靠性、监控、流量控制等方面处理。这种选择的问题是&#xff0c;在较低较低的操作难易满足应用层的问题。联想end-to-end&#xff08;端到端&#xff09;的理论&#xff0c;我们前面提到的那几个关注点实际上还是集中在应用层&#xff0c;也只能在应用层成功实现。</p>
<p>像Netflix、Twitter等SOA/微服务的早期采用者&#xff0c;他们通过建立内部库的方式处理这些问题&#xff0c;然后提供给所有服务使用。这种方法的问题在于&#xff0c;把库扩展到成百上千个微服务中难度极高&#xff0c;而且这些库相对来说是比较”脆弱“的&#xff0c;我们很难保证他们可以适应所有的技术堆栈选择。</p>
<p>程度上来说&#xff0c;Service Mesh与这些库很类似&#xff0c;但Service Mesh是与服务相邻的独立进程。服务连接到代理&#xff0c;代理反过来又与其他代理&#xff08;<code>HTTP1.1/2</code>、GRPC&#xff09;进行通信。它们是相对独立的进程&#xff0c;在应用层或应用层之下分布和运行&#xff0c;进而解决了上述两个方案存在的缺陷。</p>
<h2>Service mesh 特点&#xff1a;</h2>
<ul>
<li>应用程序间通讯的中间层&#xff1b;</li>
<li>轻量级网络代理&#xff1b;</li>
<li>应用程序无感知&#xff1b;</li>
<li>解耦应用程序的重试、超时、监控、追踪和服务发现&#xff1b;</li>
</ul>
<h2>Service Mesh 基本原理</h2>
<p>如果用一句话来解释什么是 Service Mesh&#xff0c;可以将它比作是应用程序或者说微服务间的 TCP/IP&#xff0c;负责服务之间的网络调用、限流、熔断和监控。对于编写应用程序来说一般无须关心 TCP/IP 这一层&#xff08;比如通过 HTTP 协议的 RESTful 应用&#xff09;&#xff0c;同样使用 Service Mesh 也就无须关系服务之间的那些原来是通过应用程序或者其他框架实现的事情&#xff0c;比如 Spring Cloud、OSS&#xff0c;现在只要交给 Service Mesh 就可以了。</p>
<p>Phil Calçado 在他的这篇博客 Pattern: Service Mesh 中详细解释了 Service Mesh 的来龙去脉&#xff1a;</p>
<ol>
<li>从最原始的主机之间直接使用网线相连</li>
<li>网络层的出现</li>
<li>集成到应用程序内部的控制流</li>
<li>分解到应用程序外部的控制流</li>
<li>应用程序的中集成服务发现和断路器</li>
<li>出现了专门用于服务发现和断路器的软件包/库&#xff0c;Twitter’s Finagle和 Facebook’s Proxygen。这时候还是集成在应用程序内部</li>
<li>出现了专门用于服务发现和断路器的开源软件&#xff0c;如&#xff1a;NetflixOSS ecosystem</li>
<li>最后作为微服务的中间层Service Mesh出现</li>
</ol>
<p>Service Mesh 的架构重点在于：每个服务旁边都有 sidecar 代理，代理之间组成数据平面，控制平面负责下发策略和配置。</p>
<h2>Service Mesh架构</h2>
<p>Service Mesh由data plane构成&#xff0c;其中所有服务通过sidecar代理进行服务通信。&#xff08;所有代理相互连接形成一个Mesh&#xff0c;Service Mesh由此得名&#xff09;网格同时包含一个control plane——可以将所有独立的sidecar代理连接到一个分布式网络中&#xff0c;并设置网格还包括一个控制平面——它将所有独立的sidecar代理连接到一个分布式网络中&#xff0c;并设置由data plane指定的策略。</p>
<p><img alt="" height="643" src="/images/blog/87866224/local-003.png" width="858" /></p>
<p>Control plane定义服务发现、路由、流量控制等策略。这些策略可以是全局的&#xff0c;也可以是限定的。Data plane负责在通信时应用和执行这些策略。</p>
<h2>方案</h2>
<p>目前社区Service Mesh的开源解决方案有&#xff1a;Buoyant 公司推出的 Linkerd 和 Google、IBM 等厂商牵头的 Istio。Linkerd 更加成熟稳定些&#xff0c;Istio 功能更加丰富、设计上更为强大&#xff0c;社区相对也更加强大一些。所以普遍认为 Istio 的前景会更好&#xff0c;但是毕竟还处于项目的早期&#xff0c;问题还很多。</p>
<h4>Istio 介绍</h4>
<p>Istio是由Google、IBM和Lyft开源的微服务管理、保护和监控框架。Istio为希腊语&#xff0c;意思是”起航“。官方中文文档地址&#xff1a;<a href="https://link.jianshu.com?t&#61;https%3A%2F%2Fistio.doczh.cn" rel="nofollow">https://istio.doczh.cn</a></p>
<p><strong>Istio 架构要点</strong>&#xff1a;Istio 通常分为控制平面和数据平面，控制平面负责配置、策略与证书，数据平面由 Envoy sidecar 承担服务间流量代理。</p>
<p>Istio架构分为控制层和数据层。</p>
<ol>
<li>数据层&#xff1a;由一组智能代理&#xff08;Envoy&#xff09;作为sidecar部署&#xff0c;协调和控制所有microservices之间的网络通信。</li>
<li>控制层&#xff1a;负责管理和配置代理路由流量&#xff0c;以及在运行时执行的政策。</li>
</ol>
<p>Istio架构各个组成部分。</p>
<ul>
<li>Envoy&#xff1a;Istio使用Envoy代理的扩展版本&#xff0c;该代理是以C&#43;&#43;开发的高性能代理&#xff0c;用于调解service mesh中所有服务的所有入站和出站流量。</li>
<li>Mixer&#xff1a;Mixer负责在service mesh上执行访问控制和使用策略&#xff0c;并收集Envoy代理和其他服务的遥测数据。</li>
<li>Istio Manager&#xff1a;Istio-Manager用作用户和Istio之间的接口&#xff0c;收集和验证配置&#xff0c;并将其传播到各种Istio组件。</li>
<li>Istio-auth&#xff1a;Istio-Auth提供强大的服务间和最终用户认证&#xff0c;使用相互TLS&#xff0c;内置身份和凭据管理。</li>
</ul>
<h4>Linkerd 介绍</h4>
<p>Linkerd 是开源网络代理&#xff0c;设计为以服务网格部署&#xff1a;用于管理&#xff0c;控制和监控应用程序内的服务与服务间通讯的专用层。</p>
<p><strong>Linkerd 架构要点</strong>：Linkerd 通过轻量代理接管服务间通信，并提供负载均衡、熔断、重试、TLS、指标和追踪能力。</p>
<p><strong>Linkerd 基本功能</strong>
<a href="https://link.jianshu.com?t&#61;https%3A%2F%2Flinkerd.io%2Ffeatures%2F" rel="nofollow">原文链接</a></p>
<ol>
<li>Load balancing&#xff1a;负载均衡算法&#xff0c;它们使用实时性能指标来分配负载并减少整个应用程序的尾部延迟。</li>
<li>Circuit breaking&#xff1a;自动熔断&#xff0c;将停止将流量发送到被认为不健康的实例&#xff0c;从而使他们有机会恢复并避免连锁反应故障。</li>
<li>Service discovery&#xff1a;服务发现后端集成&#xff0c;通过删除特定的(ad-hoc)服务发现实现来帮助您降低代码的复杂性。</li>
<li>Dynamic request routing&#xff1a;动态请求路由和重新路由&#xff0c;允许您使用最少量的配置来设置分段服务(staging service)&#xff0c;金丝雀(canaries)&#xff0c;蓝绿部署(blue-green deploy)&#xff0c;跨DC故障切换和黑暗流量(dark traffic)。</li>
<li>Retries and deadlines&#xff1a;在某些故障时自动重试请求&#xff0c;并且可以在指定的时间段之后让请求超时。</li>
<li>TLS&#xff1a;可以配置为使用 TLS 发送和接收请求&#xff0c;您可以使用它来加密跨主机边界的通信&#xff0c;而不用修改现有的应用程序代码。</li>
<li>HTTP proxy integration&#xff1a;可以作为 HTTP 代理&#xff0c;几乎所有现代 HTTP 客户端都广泛支持&#xff0c;使其易于集成到现有应用程序中。</li>
<li>Transparent Proxying&#xff1a;在主机上使用 iptables 规则&#xff0c;设置通过 linkerd 的透明代理</li>
<li>gRPC&#xff1a; 支持 HTTP/2 和 TLS&#xff0c;允许它路由 gRPC 请求&#xff0c;支持高级 RPC 机制&#xff0c;如双向流&#xff0c;流程控制和结构化数据负载。</li>
<li>Distributed tracing&#xff1a;分布式跟踪和度量仪器&#xff0c;可以提供跨越所有服务的统一的可观察性。</li>
<li>Instrumentation&#xff1a;支持分布式跟踪和度量仪器&#xff0c;可以提供跨越所有服务的统一的可观察性。</li>
</ol>
<h2>最后</h2>
<p>总结来说&#xff0c;Service Mesh是“时间的产物”&#xff0c;Docker、Kubernetes等容器技术直接推进了对于Service Mesh的需求&#xff0c;让复杂的系统可以被轻松部署和管理。</p>
<p>未来Service Mesh将如何发展还未可知&#xff0c;或许会像TCP/IP一样形成标准&#xff0c;或许不同工具和平台会独具一格……但有一点是确认的&#xff0c;Service Mesh对于微服务生态的价值令人难以忽视&#xff0c;能够将繁重的服务治理工作变得简单高效&#xff0c;何乐而不为&#xff1f;</p>
